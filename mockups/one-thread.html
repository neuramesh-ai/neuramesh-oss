One thread. Everything else is a layer.

There is no such thing as a chat thread, a task thread and a content thread — there is a thread, which may additionally carry a task id, a state machine, drafts, or files. Today those are three different screens with three different feature sets, and the feature set is gated on what the thread is called rather than on what it holds. This proposes the opposite rule: every capability is available in every thread; a layer appears when its data exists. Round 2 folds the facts pills and their drawer into one right rail — the panel the marketing room already has.

04 So what IS a marketing thread?

Nothing. There is no thread.kind, and after this week there can't be one — every surviving kind === 'marketing' check in the codebase is room-level, not thread-level. What we've been calling a marketing thread is two independent things co-occurring: a room that supplies brand context, and a thread that happens to hold drafts. Neither implies the other, and both compose into the same rail.

05 The appearance rule, in full

One table replaces "is this a chat, a task, or a content thread?". Nothing keys off a kind — every row keys off data that either exists or doesn't. Green rows are unconditional: those are the capabilities that stop being gated. The rail follows the same logic one level down — sections, not screens.

LayerShows whenWhy that, and not "it's a task"
Transcript & composeralwaysMentions, skills, attachments, drag-and-drop, whiteboards, run cards, file cards, post cards, image generation. A capability is a property of the product, not of a row's label.
Pinned root messagea root exists elsewhereAlready correct in chat; task threads simply never got it. Same rule, both surfaces.

Supersedes the docs/25 facts line + one-drawer rule.

Track-as-taskalwaysOff: a pill that attaches a task in place. On: the state chip. One control, two readings — the escalation valve made literal, replacing today's Tasks toggle.
What this buys, concretely. Image generation works on any draft card, because the daemon branch stops asking t.kind === 'content' and asks "which thread is this draft on". You can drag a screenshot into a conversation and see it. A conversation that produced files shows them as cards instead of nothing. The reqs/artifacts/subtasks drawer stops being a task privilege — a conversation that produced three files shelves them in the same panel. And draft_posts stops needing its refusal guard — the strip renders wherever drafts exist, so there is no thread left where a draft would be invisible.
Built, 2026-08-08. Every row in the withheld group has crossed, and the three surfaces that kept drifting are now single components — ThreadMessage, ThreadRootPin, ThreadRail. A capability-by-capability re-audit of ConvoThread vs TaskThread reports zero gaps. One correction to this page in the doing: beats were not withheld. TOOL_KINDS.declare_beats excludes 'chat' by an explicit harness ruling and beats key on task_id in the schema — so they are task-shaped like the phase dial, and the row moved to the group above. The components themselves remain two files (1486 + 373 lines), but the shared spine now owns everything that had drifted.
