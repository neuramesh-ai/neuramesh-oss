Project scope in the nav — where the switcher lives, and what it promises

The bug, and what it exposed (2026-08-01). Switching projects left the Recents rail, the ⌘Y overlay and Home's In flight showing the project you had just left — a neuramesh card reading “5 rooms · 0 open · no activity yet” above a Home listing 23 threads and a shipping task that all belonged to flowe-ai. Those lists are now scoped to the active project (fixed in code, tested). What the fix exposed is a design question: Home's needs-you queue is deliberately workspace-wide — docs/12 §6, the one written deviation in docs/06 — because a blocked agent in any project needs you regardless of which one you left selected.

So the rail now carries two scopes under one heading. The project name sits at the very top, above everything, which promises that everything below it is that project — and one row, Home, is not. George: “our design of having the project switcher top left might be misaligned as it makes it seem everything showing is for the active project… where else can we add it as a visible item/filter to make it clearer?”

The brief. ① Make the scope contract legible without deleting the deviation. ② Give the switcher a visible, always-reachable home. ③ Recents rows need to say where they live without a badge doing all the work. ④ The composer's project chip should wear the project's own icon.

The three questions each direction must answer

Q1 · Scope
Standing anywhere in the app, can you tell without clicking which lists are this project and which span the workspace?
Q2 · Reach
Is the switcher visible and one click away from every surface — not only from the rail head, and not only via ⌘K?
Q3 · Cost
What does it take from the 266px rail and from the frame — and does it survive 12 projects as well as 3?
Non-goals
Not reversing docs/12 §6 · not a second creation verb · not a per-surface preference the user has to maintain.
Direction AThe scope line — the rail's vertical order is the contract
The workspace owns the top; the project owns a line of its own, and everything under that line belongs to it. Home lifts above the line, where its workspace-wide count is simply true. The project line is a real in-place switcher (it is a dropdown today only in the composer; the head is a link to the Projects page), so the switcher gains reach without gaining a new home. Cost: one 38px row, and the project stops being the first thing you read.

Direction BThe project strip — scope becomes spatial
A 52px strip of project tiles at the far left, always visible, always one click. The rail beside it is that project, top to bottom — so the rail needs no scope marking at all, and the head goes back to being the workspace. The workspace-wide destinations (Home, and later the workspace library) live in the strip's own footer, outside any project. This is the Slack/Linear/Discord idiom, which is an argument for it (no one has to learn it) and against it (it is the most borrowed shape in the deck). Cost: 52px of frame, permanently, and a structural element the app does not have today.

RecommendationA now · C's overlay toggle and the chip icon with it · B parked until projects outgrow the head
Ship A + the overlay toggle + the chip tile. A answers Q1 with the cheapest possible material — vertical order — and answers Q2 by turning the head into a real in-place switcher instead of a link to a page (a full surface swap to change a filter is the thing worth deleting here). The ⌘Y toggle is not optional in any direction: narrowing the rail without it would silently remove cross-project search, which docs/32 §12 explicitly keeps.

Why not B yet. The strip is the strongest answer to Q2 and the weakest to Q3: 52px of permanent frame, letter-tile collisions without logos, and an overflow at seven projects. It earns its width in a workspace with ten projects and several humans — worth building the day that is true, and it composes with A rather than replacing it (the strip is the scope line, rotated).

Why not C alone. C is genuinely good and I would take its two tags into A: the pill answers “what scopes this list” exactly where you are looking. But as the only move it leaves the rail head still promising project scope over a workspace-wide Home row — it explains the exception rather than resolving it.

Change surface. App.tsx nav block: head splits into a workspace row + Home + a rule + the new .scopeline dropdown (reusing the composer chip's popover markup, so the menu is one component at two sizes) · ProjectChip gains ProjLogo in the chip body (the dropdown already has it) · HistoryOverlay gains the segmented scope control and an unscoped row set behind it · tokens.css: .scopeline / .wsline / .seg / .pbadge · docs/33 gets the scope-marking idiom (solid pill = this project, dashed = wider) and docs/06 §v1 + docs/12 §6 get the amendment that the deviation is now stated in the UI rather than only in the doc. No schema, no sync rules, no migration — every list involved is already client-derived.

Open questions. ① Does Home above the rule keep the word “Home”, or become “Needs you” now that its scope is explicit? ② Should the project dropdown list a project's live-run dot (mocked) or its open-task count, when both will not fit? ③ When you open an off-project result from the ⌘Y overlay, do we switch the active project or open it in place (docs/12 §6's build-time correction says in place — worth re-confirming now that the rail narrows around you)?
