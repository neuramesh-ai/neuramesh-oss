Post previews — a draft is a card, never JSON

The live bug (#1048, 2026-08-04). A human asked plume “can you show the drafts for x and add images for two of the posts.” The thread answered with the three posts retyped as markdown blockquotes, a ```revise fence of raw JSON bleeding into the live bubble, and — further up — a posts.json card showing the wire format as a scrollable slab of JSON. Meanwhile the product’s actual answer, SocialPostCard, was already built, already rendering, already beautiful.

Nothing here is a new component. The draft card, the horizontal strip, the hidden ‹revised:…› anchor and the previewType() classifier all ship today. The gaps are three: the wire file cards as a deliverable, a reply has no vocabulary for “show me”, and the machine payload is visible while it streams. Each closes with an enforced rule, not a prompt ask.

2 · “Show me the drafts” recalls the cards draft A2

The revise contract only knows one verb — change this. Asked to show, the model does the only thing it can: it retypes. Give it the second verb. ‹cards:a,b,c› is the exact sibling of the ‹revised:…› marker that already anchors a fresh card after a reply: hidden at render, and it re-anchors the named cards under this message instead of pasting their text.

3 · The machine wire never streams draft A3

Prompted rules break under pressure; this one is a filter. The stream sink drops every token from the moment an nm-machine fence opens (revise, nmq, nms) until it closes — so the bubble shows one honest status line instead of JSON typing itself out in front of the human.

4 · posts.json IS a preview type draft A4

The strongest version of “posts always have previews”: teach previewType() a sixth type. Then a posts file renders as posts wherever it lands — a chat-mode scratch workspace (no task, no content_items, so no cards exist), the channel Library, the mobile artifact viewer, an old task’s history. The task thread still hides it (scene 1) because there the real cards win.
