Triage before staffing

dependencies resolved at triage · the worker knows its connectors · docs/design/triage-preflight-2026-08

01What the live run did

One root cause under all three symptoms: the work was staffed before anyone asked whether it was possible. The missing connector surfaced at the END — as four tasks asking the human to go fix the thing that should have been the first question.

What happened

  1. rex creates the unit, hands it to plume
  2. plume has no search_x (leg-only) and no connector context
  3. no output contract for a research unit → the coding flow writes reply_radar/radar.py, tests, a blocked draft_replies.json
  4. next steps offer the plumbing as work: "Enable a readable X connector", "Run the saved search terms", "Create measured_candidates.json"

What happens now

  1. triage resolves the ask's declared needs FIRST
  2. nothing connected ⇒ no task is created — the dependency card goes up instead
  3. one click connects, or runs web-only with the honesty label carried through
  4. the run's own plumbing never appears as a next step again

02The dependency card — the first thing you see, not the last

Enforced, not prompted: run_playbook refuses to create the unit while a hard need is unmet and returns this card, the way MAKE_IT_A_SUBTASK and CHAT_THREAD refuse. rex cannot talk past it — and the card is never a dead end, because every line is an action.

No task, no subtask and no offer exist until this is answered.
Why a card, not prose: the answer has to ARM something — "Connect X" is a navigation, "web-only" is a run with a flag. Prose gives the human neither, which is exactly how the live run ended up with four tasks nobody wanted.

03The worker knows what it's connected to

Two gaps closed. Context: a CONNECTIONS block stages into the workspace beside the brand docs — what is live, what it grants, and the tool that reads it. Capability: search_x moves from ['leg'] to ['leg','work'], so a research unit reads conversations instead of writing software that would read them later.

04Next steps are outcomes, never the run's plumbing

The distill gains one exclusion and one bias. A step that exists only to make the run work is a dependency, not a next step.

Dropped — plumbing

  1. Enable a readable X connector
  2. Run the saved X search terms through search_x
  3. Create measured_candidates.json from real X results
  4. Generate draft replies from measured candidates

Kept — outcomes

  1. routine · weekday reply radar, 09:00
  2. research · why NSDR content outperforms sleep content
  3. task · rewrite the homepage hero around owned-site growth
The bias, stated: recurring work ⇒ routine · an open question ⇒ research · a change to the product, site or copy ⇒ task. Tasks are the byproduct, not the default — and the run's own steps are never either.
