Compute choice — where your agents run

round 1 · agents are the workspace’s; machines are the members’

00The ladder — how a request picks its machine

One rule, applied everywhere (chat wakes, task claims — today only task claims have it; chat is a raw race, which is why your requests kept landing on macbook-pro-2). Capability always gates; offline never wedges — every fallthrough is visible on the run card’s machine chip.

  1. The conversation’s machine. An existing thread keeps the machine it started on — its files, worktrees and step logs live there. Skipped if that machine is offline or can’t serve.
  2. Your per-agent choice. “My requests to scout run on macbook-pro-2.” Only machines that serve that agent’s provider are offerable.
  3. Your default machine. One setting per member: where your new conversations run.
  4. The machine you asked from — origin affinity, today’s shipped rule, unchanged as the floor.
  5. Failover. Anyone capable, after a short grace. The run card names who stepped in and why.

01The join moment — one card, first entry

Shows once, when you enter a workspace where your machine can serve but your compute choice is unset. It explains sharing in two sentences, names the subscription consequence, and the choice is the config — no settings hunt. Dismissing keeps things as they are.

02Settings → Compute — your default, and per-agent placement

The existing panel gains two things: your default machine (one row, top), and an agent placement table showing where each agent will answer you — the effective machine after the ladder, with the reason when it isn’t your default. The per-agent picker offers only capable machines; an incapable one is shown, disabled, with the reason — never silently hidden.

04Agents & Machines — capability, not provenance
