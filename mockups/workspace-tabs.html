Workspace tabs — one content area, many kinds

The ask (2026-07-30): the main content area becomes flexible and tabbed. The conversation is one tab; files, terminals, browsers and previews open as sibling tabs you can close. A floating, dismissable file pane on the right opens files into the main area. One unified surface instead of today's separate dock, artifact preview, doc overlay and studio.

The verdict: yes, and it is mostly consolidation rather than construction. NeuraMesh already has tabs with per-tab kind + cwd + url + pty state — they live in the bottom dock. It already has a read-only artifact viewer with a file list and a Preview/Terminal toggle. It already renders md/html/images/diffs. What it does not have is one place for them: today the same file can appear in three different containers with three different chromes, and none of them can sit beside another.

The precedent is strong. VS Code ships "terminal editors" — terminals opened in the editor area precisely so you "cycle through terminals the same way as open files"; Zed's dock keeps its contents and accepts any editor or tab. Both concluded that the container should not decide what may live in it. This proposal applies that to a conversation-first app: the conversation is simply the first tab.

    Stop 4bGetting back to the conversation — the ask, and what I would do instead
    The proposal: a floating ← back to conversation button, bottom-centre, whenever you are on another tab. My honest read: the navigation is already solved, and the button would be the third thing in this app doing a job one thing already does. Tab one is pinned, never scrolls out, and is one click away at all times — a second affordance for the same act is exactly the duplication the last release spent itself removing (three surfaces all saying "patch is working"). And bottom-centre is already occupied: the capacity fly-up (docs/22) is position:fixed; z-index:120; justify-content:center and docks precisely there.

    But the instinct behind it is right. The real problem is not "how do I get back" — it is "do I know I should?" Deep in a file or a terminal, an agent can reply and you will not notice. That is an awareness problem wearing a navigation costume. So: put the signal on the tab that already exists, and let the notification be a notification.

    Stop 5Implementation plan — four slices, each shippable
    The order is chosen so each slice is useful alone and nothing is deleted before its replacement is proven. Everything below reuses machinery that exists: the dock's tab records (kind · cwd · url · pty), the artifact renderers, the file-read IPC the editor already uses, and the `runtimeFor`/worktree paths.
    Slice 1

    The strip + the model

    A pure tabs.ts: the tab record (id · kind · title · scope · dirty), open/close/activate/reorder, the conversation-tab invariant (always index 0, never closable), and the "reuse an open tab for the same file" rule. Unit-tested with no renderer.

    Ships: the strip renders with the conversation tab only — invisible to users, provable in tests.
    Slice 2

    Move the dock up

    Terminal and browser tabs render in the content area from the same records the dock uses; the dock becomes a launcher that opens tabs, then retires. The pty/webview lifetimes move with them.

    Ships: terminals and browsers as real tabs; the bottom dock is gone.
    Slice 3

    Files + the floating pane

    File tabs (Edit · Preview · Diff), the dismissable right pane over the worktree or the task's artifacts, ⌘P open-file, and the ＋ flyout. The artifact overlay and doc overlay start routing here.

    Ships: the surface George drew — files open beside the conversation.
    Slice 4

    Split + persistence

    Two tab groups side by side, per-session tab restore, and the retirement of the old overlays once nothing routes to them.

    Ships: conversation-beside-work, and tabs that survive a restart.
    Invariants (enforced, not prompted): the conversation tab cannot be closed or reordered out of slot 0 · a file tab is keyed by absolute path so one file is one tab · a read-only artifact tab cannot enter Edit mode (the tab record carries the capability, the UI never offers it) · closing a terminal tab kills its pty in the same action, so no orphan process outlives its tab · the code-surface boundary is unchanged — NeuraMesh reads, reviews and runs; edits stay the agent's job unless the human opens Edit deliberately.

    Budgets: tab switch <100ms (docs/05 view-switch budget applies — the tab strip IS a view switch) · a file tab opens in <150ms for files under 1MB · no tab may hold a pty or webview while hidden more than N minutes without saying so.

    Open questions for this review: ① does the conversation tab travel with the room (switch room → tab one becomes that room) or does each room remember its own tab set? ② do tabs live per-session or one global set — answered by the code: global set, per-tab scope, exactly as the dock does it today. ③ should the file pane default open on a task with a worktree, or always start dismissed? ④ is Edit in scope for v1, or Preview/Diff only until the docs/09 code-surface boundary is revisited? (My recommendation: Preview/Diff for v1 — it is the smaller, more defensible surface and it is what the review cockpit was always specified to be.)

    Ruling wanted on Stop 4b too: live-state-on-tab-one + a bottom-right peek (my recommendation), the floating back button as originally asked, or both.

    Slice 1 gets one more job from the survey: fix the z-order so the content area can host a terminal beside an open session — the defect above is the reason slice 2 is worth anything.
