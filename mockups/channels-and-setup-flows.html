Channels in the open · default rooms · setup flows

Design round for four asks: make channels visible and make a thread say which room it lives in; ship the four default channels pre-selected; reach project settings from the nav (and stop showing archived projects); and make an abandoned channel setup recoverable by giving it a thread.

Every scene is drawn from the real tokens in tokens.css and the real class metrics (nav = 266px). Both themes, side by side, because a nav that only reads in graphite is half done.

1 Channels stop hiding behind a hover

Today a project's rooms live behind a # button that only appears on hover of the project row (App.tsx:7602) — so on a touch pass, a screenshot, or a first look, the workspace appears to have no channels at all. Meanwhile every thread row already knows its room: r.channelSlug is computed and then spent entirely on a title tooltip.

The proposal: a persistent channel strip under each project head, and the room promoted out of the tooltip onto its own line above the thread title. The list stays recency-first — that is deliberate and I did not change it. Nesting threads under channels would sort by room instead of by time and turn the rail from "what I was just doing" into a file tree.

4 Projects cog · archived projects · the archive toast that exists but never shows

Three separate things, one section.

The cog — added to the Projects section head in §1, opening the All-projects page (the surface that already owns rename / archive / delete). It sits left of ＋ so the creating action stays rightmost.

Archived projects in the nav — root cause found. nm:workspace-meta selects from projects p where p.workspace_id = ? with no status filter (sync.ts:1687), so archived rows sync down and navTree renders them — its projects parameter has no status field at all, so it cannot filter. The Projects page filters client-side and looks fine, which is why this hid. Two prop type comments in App.tsx already claim "active (non-archived) only"; both are false today.

The archive toast. It already exists, already offers Undo, and already names Settings › Archived chats — but it renders inside roomhome only (App.tsx:20498). Archive from the nav rail and you are not on that surface, so you get silence. That is precisely the trap the code comment three hundred lines above it warns about: one row-set, three renderers.

5 Setup flows — an abandoned setup becomes a thread you can finish

Today the marketing setup is a card rendered from absence: the room shows it because channels.marketing is null. Walk away mid-way and nothing was created — no thread, no task, no queue entry — so there is no object to come back to. The card is the only door and it only exists while the room is empty.

The proposal: a channel gets a setup thread the moment it is created. It is a task-shaped thread so it is trackable, it holds a human gate so it lands in needs you, and it survives abandonment because it is a row, not a rendering condition.

How it generalises

The point of building it this way is that marketing is just the first flow. A flow is a declaration; the thread, the queue entry, the progress bar and the resume behaviour are shared machinery that never has to be written twice.

The registry

// packages/shared/src/setupflows.ts — pure data + a pure reducer, like beats.ts/stall.ts export const SETUP_FLOWS: Record<ChannelKind, SetupFlow> = { marketing: { id: 'marketing.v1', // versioned: a changed flow re-runs, an unchanged one never does title: 'Set up your marketing HQ', owner: 'marketer', // falls back to the room's orchestrator steps: [ { id: 'product', kind: 'text', writes: 'marketing.website' }, { id: 'goal', kind: 'text', writes: 'marketing.goal', optional: true }, { id: 'focus', kind: 'pills', writes: 'marketing.focus' }, { id: 'connect', kind: 'connectors', optional: true }, ], onComplete: 'marketing.bootstrap', // the schedule that already exists today }, // build: { … } — the next one is a data entry, not a feature };
Everything user-visible in §5 is derived from this: the step labels, the n/4 counter, the progress bar, which step resumes, and what "complete" means.

The moving parts

PieceWhat it isWhy this way
The threadA task with kind:'setup', created with the channelYou asked for trackable states, and a task already has them. But it must not ride the full board FSM — no offer, no claim, no reviewer, no acceptance. It follows the subtask precedent (docs/24): a lean todo → in_progress → done with cancel as the other valve.
Needs youAn open setup step is a human gateneedsyou.ts already routes on "who holds the ball". A setup task whose current step awaits a human answer holds it — no new queue, no new badge logic.
ResumeAnswers write to channels.marketing as they landThe current card holds all four answers in React state and commits once at the end — which is exactly why abandoning loses everything. Writing per step is what makes the thread resumable at all.
IdempotenceUnique on (channel_id, flow_id)Backfill, channel re-creation and two desktops racing must all converge on one setup thread. The same constraint shape as the wake-dedupe index (0060).
BackfillBoot pass over channels with a flow and no threadSame idempotent-boot-backfill path the skill packs and the bosun seat already use — so existing projects get theirs without a migration dance.
Opt-outCancel the taskSomebody who does not want a marketing HQ needs a way out that is not "ignore this forever". Cancel closes the thread and the room behaves like any other.
The one thing I would push back on. Making setup a board task in the full sense would put "Set up your marketing HQ" on the board next to real engineering work, in a column, needing an assignee and an acceptance. That is why the table proposes the lean subtask-style lifecycle instead: trackable and visible in the queue, but never a card the reviewer pool can pick up. If you want it on the board proper, that is a different and heavier design — worth saying out loud before I build either.
Open question. Backfill on release will create a setup thread in every existing marketing room — including rooms already fully configured. The safe rule is only create where the flow's writes targets are still empty, so a configured room stays quiet. Confirm that's the behaviour you want, or whether configured rooms should get a "review your setup" thread instead.
