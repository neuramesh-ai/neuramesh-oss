Four phone fixes

George ran the TestFlight build on a real device and found four things. Each one below says what he saw, what is actually wrong in the code, and what the screen becomes. Frames are the app's own tokens, at phone width, in both review themes.

1

The session list arrives in pages

“It grows very long, the device gets hot, and it sort of disappears and then the muggled text shows.”

Why it happens

  • The thread query asks for 300 rows and runs one correlated subquery per row for the last message. PowerSync re-runs it on every message any agent writes.
  • The task query has no limit at all, and carries each description.
  • Both re-derive in JavaScript on every change, then the list keeps all of it in memory.
  • The garbled overlap is the list recycling rows against estimatedItemSize={56} while rows are taller and vary.

What changes

  • The list loads 25 sessions, then 25 more each time you reach the end. The query pages by updated_at, so the work is bounded.
  • The last message leaves the list query. A row's snippet comes from the row itself.
  • A session row is a fixed 64px, one line of title and one of snippet, so recycling has nothing to guess.
  • The needs-you queue's dead line becomes a control: Show 4 more, four at a time.

2

The Code composer names its model

“It doesn't seem like I can select a model in the Code view on mobile.”

Why it happens

  • The open message already carries modelId, and the desktop sets it from its model selector.
  • The phone never sets it, so every session silently inherits the project's developer default and the screen says nothing about which brain is working.

What changes

  • A model chip joins Plan·Act, the project and the machine. It shows the model the session will use.
  • Tapping it opens the same grouping the desktop uses: the NeuraMesh starter brain, then a group per provider.
  • A provider with no credential is visible and dimmed, with the reason, rather than hidden.
  • The Code thread's head wears the model as a tok, so a session you return to says what ran it.

3

The calendar shows the work, not only the clock

“Calendar seems to be showing routines instead of items, e.g. posts that are scheduled, and draft items as draft, which users can click, edit and reschedule.”

Why it happens

  • The post lane exists, but it plots a post only when it already has a time. A draft with no slot is dropped, and drafts are most of what a person has.
  • Everything in the agenda is display-only. There is nothing to tap.
  • So a week of routine firings is all that ever shows, which is what George saw.

What changes

  • Drafts without a time get their own band, Waiting for a time, above the week. They are the work, so they are not hidden.
  • Every agenda entry is a target. A post opens a sheet: the platform, the text, the picture.
  • The sheet does what the desktop's does: Generate a picture, set a time, reschedule, unschedule, approve.
  • A routine firing stays a firing and opens its routine.

4

No repo is an offer, not a dead end

“When Code says no repo for a project, it should provide a link or button to set up a repo.”

Why it happens

  • The composer's note says no repo attached to this project as plain text, so the sentence names the problem and offers nothing.
  • A Code session without a repo can only ever read, and the screen never says how to change that.

What changes

  • The phrase becomes a link: Attach a repo.
  • It opens a card in place, above the composer. Repos already in the workspace come first, one tap each.
  • Below them, Add by URL with the branch, which is repo.link, the same command the desktop sends.
  • A folder on a computer stays a computer's: the card says so rather than offering a picker a phone cannot honour.
