Code on your machine

The desktop app is a workspace machine, and it becomes a Code host. Where a session runs is a choice you can see: the composer says which machine will answer and lets you pick another; a desktop-only default sends sessions you start on this Mac to this Mac; sessions born on the web or from a routine prefer the cloud. One rule, three surfaces.

1

The machine chip — the composer's third knob

Beside the room chip and the brain pill: where this session will run, said in the same chip idiom, with the reason in its popover. It designates the session; per-agent choices stay in the Compute panel. The list is the Compute panel's rows, one line each — glyph · name · owner · state — with Auto first and the default marked. A machine that cannot run the work is listed with its reason and cannot be picked.

2

The same chip in Code — it names the host to dial

In Code the chip is not a preference the ladder honours later; it is the machine the engineering channel opens to. This Mac means the app's own engineering host, in process, no relay in the path; a cloud or member machine means the relay lane. The project and model chips stay where they are; the machine chip closes the row.

3

Compute — the default, and rows that say their kind

One new row, drawn only by the desktop client: sessions you start on this Mac run on This Mac or Auto. It lives in the member's compute prefs beside the per-agent choices, so it syncs like they do and never appears on the web. And every machine row states its kind — this Mac · cloud · member machine · shared with you — so "Cloud machine: awake" can no longer describe a laptop, which is what the dev stack's pill is doing today.

4

Where a session runs — the rule the ladder enforces

A session runs on the machine it was designated to, else on the machine of its origin. Continuity outranks both: a thread that already ran somewhere keeps running there. The designation is a column, the rule is shared pure code with tests, the claim is a lease — nothing here is a prompt.

D9 · The rule above. It extends the shared-compute ladder rather than replacing it: a new designated rung reads the thread's own machine before the prior run's, and a new origin rung applies the defaults. Per-agent choices and consent grants are untouched.
D10 · The chip designates the session, never the agent. Per-agent placement stays in Compute. A chip that could pin an agent would be a second copy of that panel in every composer.
D11 · The desktop-only default is per member, and the app hosts Code as the signed-in member. A laptop is one person's; the setting lives in their compute prefs. Hosting needs no machine token because the app runs the session for its own user. Letting other clients reach this Mac through the relay is a later entry in the same list, and it would say so until it lands.
