# First run: the doors (2026-09-19, a blocker)

Canvas: https://claude.ai/artifact/9sEXxHo3MQtxy1HLCnTVKE. Boards and `canvas.json` beside this file
are generated by `build.mjs`.

## The ask

George, on the first run of v0.138.0 after the stack came up: "it seems to be taking me through
onboarding again and i don't see a sign in or create an account first page, i already have an
account, i don't want to setup again … the start free option should allow users select cloud
workspace or local; if local is when we set up the fully local setup still allowing them migrate
later, but if cloud, we take them through the onboarding but setup a cloud workspace and log them in
(no need for the docker containers based flow here)".

## Why it happened

The shipped app (no `NM_AUTH` lane) makes the Local connection first and adds the Cloud connection
only once a Clerk session is stored (`main/connections.ts planConnections`). `pickForeground` puts
the cloud in front when a session exists. George's old session was not found by the new build, so
the local stack booted, the fresh local workspace reported `needsOnboarding`, and `App.tsx` opened
the wizard. Nothing before the shell offers Sign in: `Login.tsx` renders only on the Clerk lane, and
the one cloud door on a local connection is Get Pro inside the shell (Settings › Connections, the
rail foot, the PLAN_LIMIT gate).

## What exists (reused, not rebuilt)

- **The hosted hand-off**: `main/auth-clerk.ts loginViaHostedWeb` opens `neuramesh.app/desktop-signin?nonce`
  and polls `/auth/desktop/poll`. The page (`apps/web/src/account.tsx DesktopSignIn`) has both faces:
  `mode=signup` creates the account (the phone's Start free lane, D15). `main/upgrade.ts` has the
  15-minute cancellable poll (`pollDesktopAuth`), the `/pro` sign-up-then-pay page (`proPageUrl`),
  and `finishUpgrade` (save the session, add the cloud connection, wait for the plan, foreground).
- **The first workspace**: the server creates one at the first hosted sign-in (`first-workspace.ts`)
  with no crew, so `listWorkspaces` reports `onboarded = false` and the desktop wizard RESUMES on it
  (`wsident.ts pickBootWorkspace`, `resumeWorkspaceId`): Machine · Keys · Team · Launch adopts it.
- **The local lane**: the chain card (the first-run stack round) and the local wizard.
- **A dormant Local**: `localIsDormant` already keeps the stack off for a cloud user; `nm:local-stack-start`
  wakes it from Settings › Connections and the foot. **Move to Cloud** (H1, H2) migrates later.
- **An invitation beats the wizard** (`InvitedFirstRun`, 0113).

## The decision (George, round 2, 2026-09-19)

"where should your workspace live, instead of where does your workspace live; it should be clear
that they can upgrade anytime to cloud; This Mac, instead of on this mac, The cloud instead of in
the cloud; cloud should indicate free 500 credits to get started; use icons for the cloud and this
machine; also indicate they get cross device sync across mobile, web and desktop devices".

So the cloud row is **free, with 500 credits to start** (the Individual model of 2026-09-03). What
that pulls in, because two rulings of 2026-09-12 (source release, U1a and U1b) point the other way:

- **The signup grant comes back**: a free hosted account's first workspace gets 500 credits once
  (`grantCredits(…, 'signup', <workspace id>)`, deduped by note), so the starter brain answers
  without a key. The grant was removed on 09-12 (docs/07: "no signup grant").
- **The hosted write gate stands down for free hosted workspaces**: `NM_HOSTED_FREE_GATE` stays `0`
  (it was scheduled to flip on 2026-09-29), and the desktop's `hostedrule.ts` no longer replaces the
  composer on a `free` hosted workspace. The seat cap (1), the project cap (3) and the machine cap
  (1) stay: those are the entitlements table, not the gate.
- docs/07 is amended. The site's "Free is your Mac. Pro is the cloud." line and the 09-15 notice
  to hosted-free owners are George's follow-ups, named in the PR's deploy notes.

## The build

**Main** (`apps/desktop/src/main`)

1. `firstrun.ts` (new): `isFreshProfile({ clerkSignedIn, storedForeground, localUsedBefore, custom })`
   (pure, tested) and the door's state machine
   `choose → waiting(door, url) → landing → done | expired | error`, cancellable, with a reopen.
   `choose('local')`: start the stack, boot the dormant Local, put it in front. `choose('signin')`
   and `choose('cloud')`: `startDesktopAuth`, open `/desktop-signin?nonce[&mode=signup]`,
   `pollDesktopAuth` (the server nonce's fifteen minutes), then the landing: save the session, add
   the cloud connection, put it in front. No plan wait: the workspace is free. Local stays dormant on
   the cloud lanes. A dev build with no cloud address says so instead of failing a fetch.
2. `firstrunipc.ts` (new): the fresh-profile fact (computed BEFORE `startLocal()`, the Local
   connection goes dormant on a fresh profile), `nm:first-run-state` · push `nm:first-run` ·
   `nm:first-run-choose { door }` · `nm:first-run-reopen` · `nm:first-run-cancel`.
3. `index.ts`: two lines, the registration before `startLocal()`. Everything else unchanged.

**Renderer** (`apps/desktop/src/renderer/src`)

4. `views/FirstRunDoor.tsx` (new): the five states on the `.lsg*` recipes (the card and the status
   row exported from `LocalStackGate.tsx`), `role="radiogroup"`, arrow keys and Enter. Copy in one
   `FIRST_RUN_COPY` object (CLAUDE.md #11). `.lsgglyph` and `.lsgrow.place` in tokens.css.
5. `bridge/nm.ts`, the preload, `preview/mock-nm.ts`: the five lanes, one-liners (the mock-drift test
   reads all three; the two mirrors' ratchet caps rise with a dated reason, as every lane before).
   `?firstrun=choose|waiting|waiting-signin|landing|expired|error` seeds the harness.
6. `shell/useBootGates.ts` (new) owns the door's state and the stack payload; `App.tsx` gains one
   branch before the stack gate: while the door is not `done`, the door is the screen, and auth is
   read only once it is. After `local` the chain card takes over as today; after a cloud lane the
   foreground push remounts the shell, the boot resolves memberships, and the shell, the invitation,
   or the wizard resume follows, exactly as for a cloud user today.

**Server** (`packages/control-api`): the 500-credit signup grant at a free hosted account's first
workspace (`first-workspace.ts grantSignupCredits`, the ledger's `signup` kind, best effort behind
the creation), `NM_HOSTED_FREE_GATE` stays `0` (a deploy note, no code), docs/07 amended.
**Desktop**: `shell/hostedrule.ts` answers false for every plan. **Web**: the pricing copy is a
follow-up for George.

- Live (done 2026-09-19, the built app on a FRESH `NM_USERDATA` profile, no `NM_AUTH`, driven over
  CDP): the door came up with nothing built (no `local_stack` line, no `brain/local`); Sign in
  opened the real hand-off page in George's browser, which was already signed in, so the session
  landed in seconds (`waiting → landing → done`, `foreground_swap … to=cloud`); The cloud opened the

  `neuramesh-local-*` containers; the lane is the existing `nm:local-stack-start` path unchanged),
  and the post-landing shell boot (it would register this Mac as George's machine a second time).

## Assumptions (correct me or I proceed)

- The stored session of the old cloud app is not recoverable in the new build, so the door is the
  fix; a session that IS found keeps today's rule (cloud in front, no door).
- A profile that ever ran the local stack (its `.env` exists) never sees the door again: the door
  is for a fresh profile only. Sign in stays available later through Settings › Connections.
- "This Mac" is preselected (the sub says the cloud is one upgrade away).
