## 2. Root causes (structural)

1. **A routine's ask could die on "no compute" and never resume.** The no-compute notice is an
   answer to every re-answer mechanism we have, and nobody re-asks on a routine's behalf.
2. **The hands-off floor keyed on a field the CLIENT chooses to send.** `task.create` learns
   "routine" only through `originThread`. The monitor sweep is a legitimate creation path ("create
   for a dropped request") with no conversation to anchor, so anything it filed for a routine was
   born gated. Doctrine §4: the server must not depend on the caller remembering.
3. **The design leg had no hands-off path** (`routinePlanApprove` and `routineAccept` exist;
   nothing approved a routine's design round).
4. **Two honesty leaks.** `dispatch.ts` re-ran the plan judgment on already-approved plans at boot,
   and the `create_task` tool told rex "say the plan awaits their review" even when the server had
   just returned `planApprovedAt`.

**Litmus:** faster (a routine never waits on a person again, and resumes the moment compute is
back) · safer (the floors move into the server and into deterministic host code; the monitor can
no longer file a routine's work off-anchor) · delightful (the thread reads as a run that happened,
not a queue of asks). Yes.

## 3. What was decided

- **A routine's ask is re-asked, by code, until it is answered or superseded.** A new host sweep,
  `routineresume.ts`, runs on the watchdog tick: a routine thread born in the last 24h whose opener
  got no real answer (nothing at all after a 10-minute grace, or only compute notices) and that
  anchors no unit is re-asked by posting the prompt again **as the owner into the same thread**
  ("Routine resumed · title"). That is a fresh human trigger, so every existing mechanism applies
  unchanged: the placement ladder, the wake lease, the exactly-once reply index, the thread wake
  that carries `convoThreadId`, and therefore `originThread`. Bounded: three re-asks per thread
  (counted in the thread itself, so a restart cannot reset it), never while a newer run of the same
  routine exists, only from the origin's own machine, only when this host holds a usable credential.
- **The monitor never sees a routine's thread.** `sweepTranscript` excludes messages in routine
  threads, so a sweep cannot triage a routine's ask flat (enforced in the query, not in the monitor's
  prompt: a sentence there tripped the prompt ratchet and would have been the weaker law anyway). A routine thread has a deterministic owner
  now (fire → wake → resume → unit), and "fell through" is the resume's job, not judgment's.
- **Hands-off through the design gate too.** `routineDesignFollowup`: a `propose_design` landing a
  repo-less, routine-anchored unit in `design_review` auto-approves server-side, sourced to
  `machine:routine` (the plan precedent), promotes the round to the library, and posts one line in
  the thread. A plan-first unit returns to `todo`; a host watch (`planroute.ts`) then offers the
  build to the room's worker mechanically, exactly as an approved plan is offered. Repo floors hold:
  code merges on a human whatever opened the thread.
- **Honesty everywhere the stamp is visible.** The plan judgment skips an approved plan on every
  path; the tool result tells rex the unit *started*; the design-review notify skips routine units;
  the stall classifier does not call an approved plan "awaiting the human"; the plan card's compact
  record reads **auto-approved · routine**; the unit card's line reads *approved, awaiting its offer*.
- **Not changed:** the human path. A human's conversation keeps every gate. Playbook units keep
  their existing contract (born approved, lean to the accept gate).

## 10. Round 5 (2026-09-17): the notice that cannot be missed

George, on the live result: *"the message '@rex cannot run…' is easily missed, so we should

### 10.1 The root gap, then the surface

- **An auth card never became a needs-you item.** The server mints decision rows from `nmq` cards
  only; an `nmauth` card pushed a phone notification and nothing else, so the thread pill read
  "settled", the Home queue and the bell counted nothing, and the one sentence in the transcript was
  the whole signal. Now `POST /v1/messages` mints a decision from an agent's auth card too (question:
  *"@rex cannot run here. This machine has no OpenAI / Codex login. Sign in again, or switch this
  conversation to the NeuraMesh brain."*), in the same choke point, transactional with the message.
  It leaves the queue the way a prose-answered question does, on the person's next reply. A card
  that RECORDS a switch a routine already made (`switched: true`) mints nothing.
- **The routine's switch is data now.** The auto path posts the reason WITH the card, marked
  `switched`, so the thread can show what happened without parsing prose.
- **The docked bar** (`thread/BrainNotice.tsx`, artboard F, `evidence/notice-bar-*.png`): the
  attention bar's anatomy above the composer in both threads, from ONE pure derivation
  (`packages/shared brainnotice.ts`) over the newest auth card and the conversation's brain override:
  `needs` (amber: nothing moved, the conversation waits) · `switched` (quiet: the seat runs on
  Starter here, by a routine or by your tap). Expanded: what happened · what to do · the same card the
  transcript shows (so the actions cannot drift), plus **Reset the brain here** on a switch. It
  stands while the condition stands and leaves on its own: a reply the agent could give again, or a
  Reset that put the seat back. No ack state, no dismissal, nothing for the agent to write.
