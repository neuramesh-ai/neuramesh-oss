# First run: the stack starts, and when it does not (2026-09-18)

Canvas: https://claude.ai/artifact/LjazT3D7Shydw46xFnccMY (version 3 = the contract). Boards and
`canvas.json` beside this file are generated by `build.mjs`. Evidence from the real app over the
mock bridge: `evidence/` (`scripts/capture-first-run-stack.mjs`, both doctrine themes).

## The ask

George, on the first run of the packaged local-first app after a manual upgrade: "can we redesign
or improve the display of this first page when the desktop app is downloaded? also for me, i've
been stuck in the powersync step for a few minutes".

## The bug under it

The PowerSync container was in a restart loop (exit 150, `postgres query failed`), and the card
waited 90 seconds, then said "powersync not healthy". Try again could never fix it:

1. The first `compose up` tried to publish `127.0.0.1:58081`. The repository's dev stack
   (`stack-powersync-1`) already held that port. Docker refused the start: "driver failed
   programming external connectivity".
2. After that failed start, Docker Desktop left the container with `NetworkSettings.Networks = {}`.
   Reproduced with a throwaway container: create on a taken port, start fails, the endpoint is
   gone, the next start runs with no network at all (`nslookup pg` says "Network is unreachable").
3. Every later start (the restart policy, and every Try again, which is `compose up -d`) ran
   PowerSync with no network. pgwire reports a connection that died mid-query as a bare
   "postgres query failed" (its own `TODO` says so), PowerSync exits 150, and compose never
   recreates a container whose config did not change.

The same image with the same config in a fresh container booted, migrated and activated a
replication stream, which is what proved the container, not the stack, was broken.

## The fix (main/localStack)

- **Port preflight** before a container is made: `docker ps --filter publish=<port>` names a
  container that holds the port (our own from a previous session is fine), else the OS is asked to
  bind it and `lsof` names the holder. The card: "Port 58081 is in use by another program" ·
  `127.0.0.1:58081 · held by stack-powersync-1 (Docker)` · "Stop that program, then try again."
- **A wedged container is marked**: `len .NetworkSettings.Networks == 0` on any service, and `up`
  runs `compose rm -sf <service>` first (never a volume flag).
- **A crash loop ends the wait in seconds**: every poll reads status, exit code and restart count.
  Three sightings of `restarting`/`exited`, or a restart count that grew by two, end the wait with
  the container's last error-level log line as the detail, and mark the service for recreation.
- **Try again recreates what failed**: the services a `StackError` names, or the ones a compose
  error text names (all of them when it names none).
- Tested in `index.test.ts` against a scripted Docker, with a fake clock.

## The failure card

Three parts, or one: the cause in plain words, the container's own last line in a warm well, and
the remedy. `COPY DETAILS` puts the three on the clipboard. An error with no diagnosis (Colima did
not start.) keeps the two-line card.

## Lessons

- A retry that re-runs the same command is not a retry. Compose keeps a container whose config did
  not change, so "Try again" has to remove what failed before it runs `up` again.
- A 90-second timeout with a one-word verdict hides a diagnosis the daemon already had: the
  container's status and its last log line are one `docker inspect` and one `docker logs` away.
- The card listed the containers in a hand-picked order that was not the boot order, so the
  "waiting" row was the one that had not been asked to start. Order is content.
