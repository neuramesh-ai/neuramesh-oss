**Owns:** what the human sees when the harness runs · which surface narrates · the components each phase touches
**Depends on:** [05 Execution](05-execution.md) (runs/turns) · [04 Subagents](04-subagents.md) (the tree) · [02 Communication](02-communication.md) (the events)

---

## 1. Scope

The harness is mostly invisible by design: it changes *how* an agent executes, not what the board
permits. But four of its capabilities are visible, and one is a surface that does not exist yet:

| Capability | Visible as |
|---|---|
| subagents at any depth | a **recursive run tree** in the transcript (§3) |
| streaming from a whole tree | **one narrator**, and a dock line that names the deepest active leaf (§4) |
| `park` | a **new non-terminal run state** with a shape, not a hue (§5) |
| the gate on every runtime + depth | permission cards with a **turn path** (§6) |
| a portable brain | **move-to-a-new-machine**, the one genuinely new surface (§8) |

Per [docs/33 §11](../33-design-system.md), this round is a **design review before implementation**. The
mockup is the contract; §9 says what needs signing off and when.

---

## 2. Motivation — the constraint that shapes all of it

A turn tree can hold twelve agents. Twelve narrators is not a feature; it is the duplicate-narrator
defect [docs/26](../26-live-status.md) spent a release deleting, and [docs/29 §10](../29-runs.md) names
the failure mode precisely: *a fourth thing narrating one piece of work*.

Today's live surfaces already number four — the ghost bubble, the run card, the run dock line, and the
beats ticker — and they are kept coherent by two rules that must survive this change: **the dock stands
down while its own card is on screen**, and **a wake run and its ghost are one story, so only one of
them speaks**.

So the design question is not *what streams* but *where each event lands*. §4 answers it exhaustively,
and the answer is the thing to approve first.

---

## 3. The run tree

The card is today's `.runcard`, rendered in the message stream (which is what makes it zone-legal by
[docs/25](../25-task-panel.md) — it is thread content, not another docked surface). Three changes:

| Change | Detail |
|---|---|
| **recursion** | `RunTree` becomes `{ run, legs: RunTree[] }`; `runTrees()` recurses instead of collecting one level |
| **depth is the indent** | `.leg.sub` (18px) generalises to `.leg.d1/.d2/.d3`, capped — deeper levels reuse `.d3`'s indent |
| **two new elements** | `.legseat` (role · model, mono dim) answers *which subagent is this, on what*; `.runroll` is the subtree roll-up so a **collapsed** card still states its shape |

> **The bug this fixes, stated exactly.** Today a grandchild run is not flattened — it is **orphaned**.
> `runTrees()` filters any row with a `parent_run_id` out of the root list, and only maps direct
> children, so a depth-3 run renders **nowhere at all** (`App.tsx:1941–1957`). Unbounded depth is
> therefore not a cosmetic improvement; without it, subagent trees would silently lose rows.

**Collapse past depth 2.** Depth is unbounded, attention is not. A level-2 parent shows `2 below · 1
running` and a `▸`, expanding that branch alone.

**Why a deep tree does not read as stripes:** the existing rule `.leg.on.sub { background: none }`
already drops the live fill from a fanned-out row, with the comment *"Depth is the indent; the fill
stays on the row that owns the fan-out."* That rule was written for one level and is exactly right for
n. The design system had already solved this.

## 4. Event streaming — the narrator rule

> **The parent's run card is the single narrator for its whole subtree.** A subagent never mints its
> own ghost bubble and never its own run card.

Exhaustively, where each harness event lands:

| Event | From | Lands |
|---|---|---|
| text delta | a **subagent** | that leg's `.legverb` line. **Never a bubble.** |
| text delta | the **level-1 agent** | the ghost bubble, exactly as today — it is the one producing the human-facing reply |
| `progress` envelope | any depth | the leg row (`step`, `done/total`) and the beats tracker |
| tool intent | any depth | the activity log. Only an `ask` surfaces to the human, as a card (§6) |
| gate verdict | any depth | the ledger; an `ask` becomes the card |
| `result` / `failure` | a subagent | its leg's mark + summary line, then the parent's roll-up |
| settle | the level-1 agent | the run card's terminal state, then its posted reply |

**There is deliberately no fifth surface.** If an event does not fit a row above, it does not reach the
thread.

### 4.1 The dock line

`RunDock` — one line in the ticker slot above the composer, already standing down while its card is on
screen. With a tree it shows the **deepest active leaf plus its path**:

```
◔  rex   direction B › empty + error states   writing states.html        3/7
```

The path is what makes a scrolled-away tree say something *true* rather than something stale. Without
it, the dock would report the root's title while the actual work is three levels down.

## 5. `park` — a new run state

`RUN_STATES += 'parked'`; **`RUN_TERMINAL_STATES` does not change**. That single decision means
`isRunOpen` stays true, so the rail's live row, the run dock, and the phase ring all keep painting a
parked run with no change to any of them.

**The mark is a shape, not a hue.** The runs card is monochrome by design — *"SHAPE carries state
(pulse / check / bar), the hue stays out of it"* — and **bar was already in that vocabulary**, so parked
is a **pause-bar pair**: unmistakable against the pulsing dot (running), the check (done), and the
hollow ring (stopped), introducing no new colour.

**The ring holds instead of breathing.** `.rring.parked` keeps its `--frac` and drops the pulse
animation. Running breathes; parked holds; settled fills. Three states, three behaviours of one
element.

Copy: `waiting on CI` as the leg name, `resumes on the check` as the verb, and `no tokens spent while
parked` in the card foot — because the cost question is the first one a human asks about a run that
looks stalled.

## 6. Permission cards — provenance

The gate reaching every runtime and every depth ([03](03-tools.md) T3) means a card can now be raised by
something that is **not a teammate**. One new line, `.qprov`:

```
rex › direction b › token audit                      HIGH · SHELL.EXEC
```

**The title still says the level-1 agent** (*"rex wants to run a shell command in #1046"*), because rex
is the actor and the one accountable ([04](04-subagents.md) §3.4.2). The path says which part of rex's
tree wants it. Everything else is unchanged: the agent's own elicited intent, the full command in a code
block, the risk tier from `policyGateOutcome`.

**Approving grants that call, never the branch.** A card is per-action; there is no "allow this
subagent" affordance, because that would be a policy edit wearing a button.

---

## 7. Beats — no component change, a populated one

`declare_beats` / `advance_beat` become bus tools in **P0**, so a tracker that is structurally empty for
two thirds of the fleet fills. No new component: a Codex-seated worker's tracker becomes identical to a
Claude-seated one, because availability is now a property of the turn rather than the seat.

This is the clearest single piece of user-visible evidence that P0 landed, and it is worth capturing as
before/after screenshots in that PR.

---

## 8. Move to a new machine — the one new surface

A settings flow, four steps: **Export** (Tier A, encrypted, passphrase required) → **Import** (refuses
to land on an existing brain without `merge`/`replace`) → **Sign in** (projects, conversations, tasks and
artifacts arrive from sync — they were never in the archive) → **Adopt agents** (re-point this
workspace's hosted agents at this machine).

Two lines of copy carry the whole security model, and they are part of the design, not decoration:

- On export: *"Your model keys and sign-in stay on this machine. You'll sign in again on the new one."*
- On adopt: *"rex, patch and iris are hosted on **MacBook Pro (old)**. Move them here?"* — naming the
  machine that still owns them, because silently stealing agents from a running machine is the worse
  failure ([01 §4.6](01-brain.md)).

Composed from existing idioms: the step cards are the provider-card recipe, the tier list is the
settings-row recipe, buttons are pills. No new stratum.

## 9. Component impact, by phase

| Phase | Component | Change |
|---|---|---|
| **P0** | beats tracker | **none** — it fills by itself on every runtime |
| **P0** | permission card | `.qprov` turn path (subagents can now raise one) |
| **P1** | — | **no UI change.** P1 is a behaviour-preserving refactor; if the UI moves, P1 is wrong |
| **P3** | `RunCard` · `runTrees()` · `RunMark` | recursion, `.legseat`, `.runroll`, collapse past depth 2 |
| **P3** | `RunDock` | deepest active leaf + path |
| **P3** | `shared/runs.ts` | `RunTree.legs: RunTree[]` |
| **P4** | `RunMark` · `.rring` · `RUN_STATES` | the parked branch, the holding ring, the non-terminal state |
| **P2** | Settings | move-to-a-new-machine (§8) |

**Unchanged and expected to stay so:** the phase ring, rail rows, board cards, the workspace tab strip,
the composer, the thread, Home, the needs-you queue. If any of these need to change, something in the
harness design is leaking into the product surface and should be questioned rather than accommodated.

## 10. Verification

- **Both themes**, cream oak and graphite minimum ([docs/33 §9.9](../33-design-system.md)) — the mockup
  carries a flip control so one file reviews both.
- **Real-app evidence** via `capture-evidence-electron.mjs` / the preview harness, not headless Chrome.
  *(Note: the in-app Browser pane is `visibility:hidden`, so `rAF`-driven animation does not run there —
  the pulse, shine, and ring behaviours must be verified in the real app or the harness, never from a
  pane screenshot.)*
- **The traps list** ([docs/33 §9](../33-design-system.md)): no cream creep (`.runcard` is `--card`), no
  border-swap hovers, no new hairlines inside the card (§9b — the card carries one, at `.runfoot`).
- **Reduced motion**: the pulse, ring, shine, and dot animations are all stilled; the mockup's
  `prefers-reduced-motion` block is the reference.
- **A depth-4 tree renders without breaking the rail** — the [04](04-subagents.md) P3 evidence gate.

## 11. Open questions — what this round is asking for

1. **The narrator rule (§4).** Sign off before P0, since it is the contract the implementation is gated
   against. *Recommendation: approve as written — it is the only option consistent with docs/26.*
2. **The parked shape (§5).** A pause-bar pair, no new hue. *Recommendation: approve; bar is already in
   the stated vocabulary.*
3. **Collapse threshold.** Depth 2 is a guess. It may want to be "collapse any branch with >3 children"
   instead of a depth rule. *Leaning: ship the depth rule, revisit once real trees exist.*
4. **Does `.legseat` show the model always, or on hover?** Always is honest and adds mono noise to every
   row. *Leaning: always — the whole point of heterogeneous seating is that the human can see it.*
5. **Should a subagent's produced files render inline** in the thread, as a task's deliverables do
   ([docs/30](../30-deliverables.md))? *Leaning: no — they are the parent's deliverables, attached to the
   parent's submission. Otherwise a fan-out floods a thread.*
